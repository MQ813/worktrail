# 프로젝트 업무일지 자동 업데이트 · 0.4

0.4.1 변경: 독립 업무일지·답변 초안 메뉴를 제거했다. 업무 기록 입력·수행일별 조회·편집·확정은 프로젝트 상세에 포함한다. 오늘 화면은 프로젝트의 기록을 모아 보여주는 요약이며, 각 기록을 누르면 해당 프로젝트로 이동한다. 프로젝트 미지정 기존 기록은 프로젝트 목록에서 연결한 뒤 편집한다. `/worklog` 예전 URL은 303으로 프로젝트에 연결한다. 원본·기록·편집 이력은 삭제하지 않는다.

공통 상단 경로·안내 문구를 제거하고 AI 연결/샘플 상태는 왼쪽 하단으로 이동했다. 발신자를 목록 제목과 같은 줄에 표시하며 본문과 편집기 행간을 1.5로 줄였다. 프로젝트 개요 편집과 부가 작업은 접힌 상태로 시작하고 빈 구역 카드를 반복하지 않는다.

## 처리 흐름

메일·Jira 수집 → 공통 classify → 답변 필요이면 draft / 업무 변화가 있으면 project_update → 프로젝트에 AI 미확정 변경 표시 → 사용자 부분 확정·수정·반려.

두 생성 작업은 독립적이다. 답변 불필요인 결정 공유도 프로젝트를 갱신한다. 프로젝트 업데이트 오류는 수집·초안·확정 기록을 되돌리지 않는다. AI는 구조화한 변경안만 반환하며 프로그램이 대상·근거·버전을 검사한다.

## 사용 방법

1. 프로젝트 화면에서 프로젝트를 만든다. JOB 코드는 자동 할당되며 API에서는 기존 JOB 코드를 지정할 수 있다.
2. 관련 문의를 프로젝트에 연결한다. 연결 시 최신 원문으로 업데이트 작업을 등록한다. 이후 같은 대화·Jira 변경은 연결을 재사용한다. 한 문의를 여러 프로젝트에 연결할 수 있다.
3. 원문에 등록된 JOB 코드가 하나만 명시되면 자동 연결한다. AI가 추천한 코드·의미상 후보는 자동 확정하지 않고 연결 단서로 표시한다. 사용자가 해제한 연결을 JOB 코드 때문에 다시 붙이지 않는다.
4. 프로젝트의 노란색 표시와 “AI 추가/수정/삭제 · 미확정” 문구를 확인한다. 근거를 펼치면 원문 링크·revision·발췌를 볼 수 있다.
5. 항목을 확정하거나 내용을 수정해 확정한다. 선택한 항목을 묶어 확정·반려할 수도 있다. 한 묶음의 검증과 적용은 원자적으로 처리한다.
6. 프로젝트나 원문이 바뀌면 이전 제안은 재검토 대상으로 전환한다. 최신 내용으로 다시 생성한다. 상충 제안은 채택하지 않을 쪽을 반려한 뒤 재생성한다. 대체된 제안은 superseded 이력으로 보존한다.

부분 확정 시 나머지 제안은 보수적으로 재검토 대상으로 전환한다. 남은 내용을 확정하려면 다시 생성한다. 가져온 문서의 남은 제안도 최신 프로젝트 기준으로 새 검토본을 만들고 이전 제안을 보존한다. 재생성은 확정·반려한 동일 입력의 같은 변경을 반복해서 제시하지 않는다. 의미상 중복 여부는 모델 판단과 사람 검토가 필요하며 문장 표현이 다른 모든 중복을 코드로 판별한다고 보장하지 않는다.

확정 TODO·회신 대기는 기존 action ID를 연결해 같은 할 일을 중복 생성하지 않는다. 프로젝트 변경 확인은 수행 실적이나 할 일의 완료를 자동 확정하지 않는다. 수행자·실제 수행일을 확인하는 기존 수행 확정 절차를 유지하며, 새 확정 수행 기록에는 프로젝트가 필요하다. 과거에 프로젝트 없이 저장한 기록은 삭제하지 않는다.

## 문서·첨부

기준 데이터는 로컬 SQLite이고 Markdown은 프로젝트 문서 출력이다. 작은 프로젝트는 index.md만 생성한다. 업무 추가 시 “별도 이슈 문서 생성”을 선택하면 issues/ISSUE-번호.md가 생성된다. 기존 제목으로 업무를 추가하면 상세 문서 설정을 변경할 수 있다. 업무 제목을 누르면 해당 업무로 기록을 좁혀 본다.

- Markdown 내보내기: 확정 내용과 별도로 표시한 미확정 제안·근거를 포함한다.
- 확정본 내보내기: 미확정 제안은 포함하지 않는다.
- JOB 폴더 ZIP: index, 필요한 issues, 원문 연결 첨부와 가져온 assets를 묶는다.
- 생성 구역 밖의 사용자 메모는 재출력 시 보존한다. 생성 구역이 외부에서 바뀌면 덮어쓰기를 차단한다.
- 외부 문서 수정 가져오기: 원본 blob을 보존하고 Markdown의 추가 내용을 미확정 후보로 가져온다. 기존 확정 항목의 자동 삭제·대체나 3-way 병합은 하지 않는다. 필요한 대체는 확정 내용 수정에서 직접 처리한다. 출력된 미확정 제안은 다시 가져오지 않는다.
- 기존 JOB 폴더 가져오기: index·issues·assets의 원본·해시를 보존하고 구역별 내용을 검토 대상으로 만든다. 개요의 목적/담당자/상태/시작일은 필드별 변경으로, 결정·다음 액션은 해당 구역의 항목으로 가져온다. 큰 문서는 분할한다.

최대 폴더 파일 500개, 파일당 20MiB, 폴더 합계 100MiB이다. 외부 개별 Markdown 가져오기는 2MiB 제한이다. 외부 파일의 실시간 양방향 동기화는 제공하지 않는다. 자동 수집에 생성 문서를 넣는 순환 처리를 금지한다.

## 설정과 운영

```toml
automatic_drafts = true
automatic_project_updates = true
# 지정하지 않으면 프로젝트 업데이트는 기존 draft_model 사용
project_update_model = "provider/model"
```

Windows 앱 worker와 CLI worker --live가 같은 설정을 전달한다. 기존 분류 저장본의 schema 1도 읽되, 새 분류는 schema 2를 출력한다. 구버전 결과에 업데이트 여부가 없으면 unknown으로 취급한다. 최초 history-only 적재는 과거 전체를 자동 갱신하지 않는다. 연결·수동 재생성은 명시적인 최신 원문 처리 요청이다.

프로젝트 상세의 “기간을 지정해 기존 이력 재구성”에서 한국 시간 기준 수집 시작일·종료일을 지정하면 해당 프로젝트에 연결한 과거 revision을 최대 500건 처리한다. 수집일 기준이며 메일 작성일·실제 수행일 기준의 검색과 구분한다. 결과에는 과거 이력 표시를 붙이고 항상 미확정으로 저장한다. 과거 revision과 생성 시점의 최신 원문 기준을 함께 보존해, 그 이후 새 원문이 도착하면 과거 후보도 재검토하도록 한다. 사용자 요청 없이 baseline 전체를 실행하지 않는다.

작업 상태·오류·재시도는 운영 상태에서 확인한다. 프로젝트/문의 상세에서 연결 프로젝트, 업데이트 상태, 원문, 검토 이력을 확인할 수 있다. 오늘 화면은 AI 미확정 변경을 별도 영역에 표시한다.

DB v5→v6 migration은 기존 원문·초안·편집·수행 기록을 보존한다. 기존 프로젝트 이름을 유지하고 JOB 코드를 추가한다. migration 전 SQLite snapshot을 생성한다. 백업은 새 모델·검토 이력·원본 blob과 runtime/projects의 문서·수동 메모를 포함한다. 복원 후에도 문서 생성 영역의 수정 감지가 유지된다.

## 검증

- 자동 테스트 83개: 기존 회귀와 신규 프로젝트 생성·검토·실패 독립성·근거 검증·재생성·반려 재실행·충돌·연결 해제·원문 변경·이관·첨부·백업 복원·기간별 이력 재구성 등을 검증했다.
- 실제 Edge: 새 프로젝트 관련 12개 화면/너비 조합, 기존 42개 조합. 입력 라벨·현재 메뉴·키보드 건너뛰기·수평 넘침·오류 없는 JavaScript·수정 후 확정·반려·저장/재로딩을 확인했다.
- 실제 Windows OpenCode/OpenAI 합성 평가 3/3: 답변 불필요 결정, TODO+회신, 단순 감사의 변경 없음. 각 사례에서 classify와 project_update의 실제 응답 및 근거 검증을 수행했다. `runtime/project-model-evaluation.json`.
- 실제 Windows 배포본: 프로젝트 연결·화면·자동 업데이트 작업 실행, 중복 실행 방지, worker 재시작 중 API 유지, 종료·재기동 후 기록 보존을 통과했다. 최종 빌드 결과는 `runtime/project-native-final-smoke/verification.json`.
- UI 결과: `runtime/project-review-1794660896654951300/verification.json`, `general-review/report.json` 및 화면 PNG.

실제 사내 메일·Jira·DRM 환경과 장기 운영 정확도는 검증하지 않았다. 이미지 의미 해석은 기존과 같이 미지원이다. 근거 발췌 일치 검증은 내용의 의미적 정확성까지 보장하지 않으므로 사용자 확인을 유지한다.

## 구현 범위와 계획에서의 구체화

생성 모델은 DB의 확정 프로젝트 항목과 미확정/반려 이력을 구분해서 입력받는다. 변경은 항목 ID 또는 work_title로 대상을 가리키며, 새 업무 제목에 대한 생성은 사용자 확정 트랜잭션 안에서 처리한다. 따라서 아직 생성되지 않은 업무 ID를 다른 제안에서 참조하는 의존 그래프를 만들지 않고 업무 생성과 기록 적용을 함께 처리한다.

자동 연결은 사용자 연결과 명시 JOB 코드부터 적용한다. 모호한 AI 후보는 수신함/프로젝트에서 검토한다. 메일 발송·Jira 댓글 게시·Jira 상태 쓰기는 추가하지 않았다. 기존 analyzers는 문서 추출 결과를 재사용하고 이미지 해석은 한계로 전달한다.

재현 명령:

```powershell
.venv/Scripts/python.exe -m pytest -q
.venv/Scripts/python.exe scripts/project_review_smoke.py
.venv/Scripts/python.exe scripts/evaluate_project_updates.py --config "$env:LOCALAPPDATA/WorkTrail/settings.toml" --live
.venv/Scripts/python.exe scripts/desktop_smoke.py --exe dist/WorkTrail-0.4.1/WorkTrail/WorkTrail.exe --output runtime/new-project-native-smoke --projects
```

평가 스크립트는 합성 입력만 사용한다. 브라우저·native smoke는 별도의 새 runtime에서 실행하며 사용 중인 데이터와 창을 수정하지 않는다.
